# دور زدن هوشمند فیلترینگ: نردبان، نه یک پروتکل

سؤال اصلی این نیست «کدام پروتکل قوی‌تر است». سؤال این است: **روی این مسیر، در این دقیقه،
کدام پروتکل هنوز کار می‌کند و چقدر می‌ارزد؟** یک پروتکل در تهران روی MCX خوب است و روی
همان مودم در کرج کشنده است؛ فیلترشکنی که این را نفهمد، فقط یک config ثابت است.

پس «هوشمند» در اینجا یعنی یک حلقهٔ اندازه‌گیری + رتبه‌بندی، نه هوش مصنوعی:

```
اندازه‌گیری مسیر ──▶ دروازه‌های سخت (چه چیزی اصلاً کار می‌کند؟) ──▶ امتیاز وزنی ──▶ انتخاب با هیسترزیس
       ▲                                                                        │
       └────────────── پروب‌های فعال + نتایج اتصال واقعی ◀──────────────────────┘
```

کد: `engine/src/probes.js` (اندازه‌گیری)، `score.js` (دروازه و امتیاز)، `tune.js`
(پارامترهای هر پروتکل)، `singbox.js` (تولید config)، `ladder.js` (جدول پله‌ها).

## نردبان: هر پله ایدهٔ یک ابزار معروف را می‌آورد

| پله | میراث | ایده‌ای که برداشته‌ایم | کِی می‌بَرَد |
|---|---|---|---|
| `hy2_brutal` | Hysteria (apernet) | pacing با BRUTAL که در لینک پرفقد جا نمی‌زند، obfs ژئو برای پُرکردن اندازهٔ بسته، پرش پورت، Chrome QUIC parrot | مسیر پرافضط + DPI که QUIC را می‌شناسد ولی الگوی کروم را تحمل می‌کند |
| `tuic_v5` | TUIC (IMUX) | `0-RTT resumption`: بعد از خواب مودم، reconnect بدون handshake | موبایل، سوییچ آنتن، latency-sensitive |
| `vless_reality_tcp` | Xray/VLESS Reality | handshake با یک **سایت واقعی** تمام می‌شود؛ نه گواهی ماست، نه Hello قلابی | وقتی active probing دارند؛ پیش‌فرض امن ما |
| `vless_reality_grpc` | v2fly gRPC | چند RPC کوچک روی یک HTTP/2 بلند | middlebox که اتصال TCP بلند را می‌کُشد؛ پشت CDN |
| `wg_uot` | WireGuard | کم‌هزینه‌ترین crypto؛ خروجی مؤثرِ ≈۱٫۵ برابر نسبت به تونل TLS | لینک تمیز UDP، CPU کم (گوشی قدیمی) |
| `anytls` | Amnezia/AnyTLS | هزینهٔ پنهان‌کاری با padding خریده می‌شود نه با crypto | می‌خواهیم شبیه HTTPS باشیم ولی ارزان‌تر از TLS-inside-TLS |
| `ss2022` | shadowsocks → Outline | سربار framing تقریباً صفر | پهنای باند کم است ولی TLS/QUIC شدنی است |
| `naive_h3` | NaïveProxy | رفتار مرورگر + proof-of-work برای probe-defense | وقتی «هیچ چیز غیرمرورگری» عبور می‌کند |
| `vless_ws_cdn` | مرز/وای‌مِش + Cloudflare | fronting روی IPهای معتبر CDN | آی‌پی دیتاسنتر بلاک است، ASN کلادفلر نه |
| `vmess_ws` | VMess قدیمی | سازگاری با سرورهای موجود | فقط opt-in؛ دیگر امن‌ترین گزینه نیست |
| `tor_bridge` | Tor/obfs4 | وقتی آی‌پی و TLS ما هیچ ارزشی ندارند | طبقهٔ آخر: سانسور سراسری |

هیچ‌کدام «ترکیب» نامرتب نیست: هر پله **یک config مجزای sing-box** است که کنار بقیه در
یک `selector` قرار می‌گیرد. پس انتخاب، جابه‌جا شدن بین config‌های از پیش معتبر است — نه
مذاکرهٔ یک پروتکل hybrid روی سیم.

> «ترکیب فیلترشکن‌های معروف» یعنی همین: بهترین ایدهٔ هر stack متن‌بازِ شناخته‌شده در یک
> نردبان که با هم رقابت می‌کنند. wrapping کردن سرویس‌های تجاری (Nord/Express/…) نه ممکن
> است (ToS) و نه قابل دفاع: کل ترافیک شما از دست یک نفر ثالث رد می‌شود.

## دروازه‌های سخت: قبل از امتیاز، شدنی بودن

امتیاز دادن به پروتکلی که کار نمی‌کند بی‌معنی است، پس این‌ها فیلترند نه وزن:

- `requiresUdp` و مسیر UDP-blocked → حذف (نه تنبیه).
- `requiresQuic` و `quicBlocked` → حذف.
- MTU: QUIC بالای ~۱۱۸۰ نمی‌تواند packet‌های ۱۲۰۰+ بفرستد → حذف؛ mss clamping جای آن نیست.
- گرهٔ مقصد آن پروتکل را listening ندارد → حذف، با دلیلِ خوانده‌شدن در UI.

هر دلیل در `ranking[].reason` می‌آید و در داشبورد نشان داده می‌شود. «چرا این انتخاب شد»
به‌اندازهٔ «چه انتخاب شد» مهم است.

## سیاست‌ها (همان پنجرهٔ کشویی‌ها)

| حالت | وزن‌ها (throughput·latency·stability·evasion·cost) | برای چه |
|---|---|---|
| `auto` | 0.34 · 0.20 · 0.24 · 0.16 · 0.06 | پیش‌فرض |
| `speed` | 0.55 · 0.16 · 0.14 · 0.08 · 0.07 | دانلود، استریم |
| `stealth` | 0.14 · 0.06 · 0.14 · **0.60** · 0.06 | دوره‌های حساس |
| `game` | 0.10 · **0.55** · 0.25 · 0.05 · 0.05 | تماس، بازی |
| `resist` | 0.08 · 0.04 · 0.12 · **0.70** · 0.06 | سانسور کامل |

سیاست فقط وزن را عوض می‌کند؛ دروازه‌ها در همه حالت سفت‌اند. یک گزینهٔ «سرعت» نباید
پروتکلی را که DPI می‌کُشد انتخاب کند، و یک گزینهٔ «پنهان‌کاری» نباید شما را به ۲Mb/s
بچسباند وقتی Reality همان‌جا ۸۰Mb/s است — به همین دلیل evasion و throughput در دو
مؤلفهٔ جدا محاسبه می‌شوند، نه یک عدد مبهم «بهترین».

## سِتی‌هایی که واقعاً کار می‌کنند (و آن‌که چه چیزی نمی‌کنند)

| تکنیک | کارکرد | هزینه |
|---|---|---|
| Reality handshake | هیچ امضای TLS ما وجود ندارد؛ fingerprint به میزبان واقعی نسبت داده می‌شود | نیاز به یک domain/پورت مشترک با سایت واقعی |
| `obfs: gecko` (Hysteria2) | اندازهٔ بسته‌ها را ۵۱۲–۱۲۰۰ می‌کند → الگوی «QUIC» دیگر نمی‌خواند | ۱۵–۲۰٪ سربار |
| `record_fragment` | شکستن record در TLS تا SNI در TCP segment تنها نماند | فقط اگر DPI بستهٔ خام را می‌خواند؛ در 1.14 این با `fragment` خامِ DPI-محور یکی نیست |
| پرش پورت | یک port-qos را دور می‌زند | اگر throttle پروتکل‌محور باشد فایده ندارد (مدل ما دقیقاً همین را می‌داند: `udpThrottled` ≠ `portThrottled`) |
| SPKI pinning | MITM گواهی جعلی را بی‌اثر می‌کند، بدون `insecure:true` | باید با هر تعویض گواهی به‌روز شود |
| `tls: {certificate_public_key_sha256}` | جای `insecure` | یک خط در config، یک لایهٔ دفاع واقعی |
| spoof/packet injection (سطح kernel) | تغییر بسته‌های واقعی روی سیم | روت/`CAP_NET_RAW` لازم است → **روی اندروید در دسترس نیست**؛ عمداً استفاده نشده |
| ECH | پنهان‌کردن SNI در TLS1.3 | به `sing-box generate ech-keypair` و پشتیبانی سرویس‌دهنده نیاز دارد؛ هنوز emit نمی‌شود |

## چه چیزی را پوشش نمی‌دهد (صادقانه)

- **IP/ASN block:** اگر کل ranges دیتاسنترها بسته باشد، هیچ پروتکلی معجزه نمی‌کند؛ ladder
  به سمت CDN-fronting یا Tor می‌رود و همین را در UI می‌گوید.
- **پایان اتصال:** ISP می‌فهمد شما به یک IP پرمخاطب وصل می‌شوید. این ابزار متادیتای اتصال را
  پنهان نمی‌کند؛ برای آن فقط چند نفره بودن مقصد (که Reality روی یک سایت واقعی می‌دهد) کمک
  می‌کند.
- **DNS نشتی:** با `fakeip` و `tun: {strict_route: true}` در config هندل شده، ولی اگر روی گوشی
  Private DNS خاموش باشد، بعضی اپ‌ها از tunnel رد نمی‌شوند؛ `strict_route: true` را روشن
  بگذارید.
- **دستگاه جاسازی‌شده / پروفایل کاری:** هر چیزی روی آن ماشین قابل read است.

## چطور خودتان بسنجید

```bash
cd engine
# شبیه‌سازی یک مسیر و دیدن انتخاب و دلیلش
node src/cli.js plan --mode stealth --access cellular --censor quic-kill --pretty

# اندازه‌گیری واقعی روی یک گره
node src/cli.js race --profile /etc/savak/profile.json --node fra-1 --repeat 3

# config حاصل را با خود sing-box هم چک کنید (اعتبار معکوس)
sing-box check -c /tmp/client.json
```

`--censor` گزینه‌ها: `none · sni-only · udp-throttle · port-qos · quic-kill · udp-block ·
deep-packet · total-recall`. هر کدام همان `link` مصنوعی را می‌سازند که پروب واقعی می‌سازد؛
پس چیزی که در این تست می‌بینید همان کدی است که روی گوشی اجرا می‌شود.

## چرا پورت اندروید همان مدل است — زنجیرهٔ ضدِ رانش

خطرناک‌ترین نقطهٔ این معماری آن است که گوشی برای عوض‌کردن پروتکل بین دو heartbeat خودش
امتیاز می‌دهد. اگر آن امتیازدهی حتی یک‌بار از موتور جدا شود، کاربر «روز بد» می‌بیند، نه
پیام خطا؛ و این دقیقاً باگی است که ماه‌ها زنده می‌ماند. پس هیچ عددی در این مسیر دستی کپی
نمی‌شود:

```
engine/src/ladder.js  ──npm run gen:ladder──▶  android/…/engine/LadderTable.kt
planForNode()         ──npm run gen:golden ──▶  android/…/test/resources/parity/golden.json
savak bundle          ────────────────────────▶  nodes[].scoringInputs      (داده، نه منطق)
```

- `LadderScore.kt` ترجمهٔ دستی `src/score.js` است، ولی اعدادش را fixture قفل می‌کند؛
  `npm run check:generated` اگر جدول یا fixture کهنه باشد می‌سوزد — پس fixture «عددی که کسی
  تایپ کرده» نیست، خروجی زندهٔ خودِ موتور است.
- ورودی‌هایی که گوشی نمی‌تواند بازبسازد — چند فلگ evade واقعاً اعمال شده، آیا hop pool هست،
  naïve روی H2 سنجیده شده یا نه، و کدام پله capability خودِ گره/دستگاه را ندارد — در باندل با
  `scoringInputs` می‌آید (`engine/src/bundle.js`). `feasibility()` عمداً در Kotlin
  بازنویسی نشده: اگر می‌شد، هر نسخهٔ اپ یک نظرسنجیِ مستقل می‌شد.
- `bash android/tools/typecheck.sh` همان چک را با `kotlinc` روی JVM اجرا می‌کند، بدون
  Android SDK: ۸۰ ردیفِ رتبه‌بندی و تأیید امضای یک پروفایل واقعی.
- `LadderParityCheck.checkDetectsMutation` یک عددِ fixture را جابه‌جا می‌کند و مطمئن می‌شود
  چک **می‌تواند** fail شود. تستی که هیچ‌وقت قرمز نمی‌شود، تست نیست.
