# سرعت: چه چیزی واقعاً عوض می‌شود و چه چیزی نه

انتظار صادقانه: این موتور **سقف‌های خودزنی** را برمی‌دارد و **بهترین مسیرِ موجود** را
انتخاب می‌کند. پهنای باندی که ISP نفروخته را هیچ config‌ی نمی‌سازد. اگر جایی نوشته شد
«با این تنظیمات ۳ برابر سریع‌تر»، دروغ است؛ چیزی که اینجا می‌توان سنجید، در پایین آمد.

## چهار چیزی که واقعاً گلوگاه هستند

### ۱. پنجرهٔ TCP/UDP — بزرگ‌ترین دزدِ بی‌صدا

`bandwidth-delay product`. تهران↔فرانکفورت: ۶۰ms × ۱۰۰Mb/s ≈ ۷۵۰KB در راه. اگر
socket buffer ۲۱۲KB باشد (پیش‌فرض قدیمی لینوکس/اندروید)، اتصال هرگز به ۱۰۰Mb/s
نمی‌رسد — فرقی نمی‌کند پروتکل چیست.

موتور `sizeWindows()` را بر اساس لینک اندازه‌گیری‌شده محاسبه می‌کند و این‌ها را emit
می‌کند: `connection_receive_window` / `stream_receive_window` (Hysteria2/TUIC/naïve)،
`initial_packet_size` (یک RTT ذخیره می‌کند: handshake در بستهٔ اول، نه سوم).

نکتهٔ مهم: ما کفِ ۱MiB/۲۵۶KiB گذاشته‌ایم، نه «هرچه ممکن». buffer‌های خیلی بزرگ روی لینک
پرافضط = bufferbloat = latency بالاتر برای همهٔ ترافیک آن دستگاه.

### ۲. PMTUD و MTU

تونل یعنی سربار: ~۸۰ بایت برای QUIC+UDP+IP، ~۵۸ برای WireGuard. اگر path MTU را ندانید،
یا packet太大 می‌شود و بی‌صدا drop می‌شود (کلاسیک‌ترین علامت: «وصل است ولی باز نمی‌شود»)،
یا fragment می‌شود و CPU/افت می‌گیرد.

`tune.js` MTU را از `link.mtuCap` کم می‌کند و برای هر پله floor خودش را چک می‌کند
(Hysteria2/TUIC: ۱۲۰۰، WireGuard: ۱۲۸۰). اگر path به ۱۱۸۰ رسیده باشد، آن پله **حذف**
می‌شود نه اینکه با بسته‌های شکسته امتحان شود. `disable_path_mtu_discovery` فقط وقتی
true می‌شود که خودمان size را می‌دانیم.

### ۳. پейسینگ: BRUTAL یا BBR، نه هر دو

`up_mbps/down_mbps` (BRUTAL) یعنی «rate-limit کن و ignore کردنِ loss». روی لینکی که
افتِ تصادفی دارد، BBR (که ما به‌صورت `bbr_profile` تنظیم می‌کنیم) بهتر است؛ روی لینک
shaped که عمداً بالای ~۸۰٪ را می‌بُرد، BRUTAL بهتر است.

قاعدهٔ ما: **BRUTAL فقط بعد از یک اندازه‌گیری پایدار**. عدد pacing را از throughput
اندازه‌گیری‌شده × ۹۴٪ می‌گیریم — نه از چیزی که کاربر آرزو دارد. بدون اندازه‌گیری، config
مستقیم به BBR می‌رود. ۹۴٪ چون pacing در مرز ظرفیت، خودش drop تولید می‌کند و بعد drop
خودش را «سانسور» تفسیر می‌کند.

### ۴. handshake و سربار CPU روی موبایل

هر reconnect روی موبایل یعنی: radio wake + TCP + TLS + 1.5RTT. `tuic_v5` با
`zero_rtt_handshake` یک RTT برمی‌دارد؛ `initial_packet_size` یکی دیگر؛
`tcp_fast_open` برای rungs TLS‌محور؛ `keep_alive_period` برای زنده ماندن NAT.
این‌ها «سرعت خالص» را بالا نمی‌برند ولی **زمانِ تا اولین بایت** را که کاربر حس می‌کند
نصف می‌کنند. CPU هم روی گوشی یعنی سرعت: thermal throttle بعد از ۳ دقیقه، و
`cost.cpuLoad` در امتیازدهی دقیقاً برای همین است (و در حالت cellular جریمهٔ باتری هم دارد).

## گره: sysctl بدون آن، config توخالی است

`server/sysctl-savak.conf` (که `server/bootstrap.sh` نصب می‌کند): `fq`+BBR،
`rmem_max/wmem_max=64MB`، `udp_mem`، `tcp_mtu_probing=1`، `tcp_fastopen=3`، ECN خاموش،
conntrack بزرگ. اگر سمت سرور این‌ها نباشد، پنجره‌های بزرگ client فقط advertise شده و
هرگز پر نمی‌شوند. این تنها بخشی است که «سرعت» در آن **واقاً** عدد را عوض می‌کند — و
روی سرور شماست، نه گوشی.

## چطور اندازه بگیریم (این تنها بخشی است که به شما ربط دارد)

```bash
cd engine

# ۱. هر پله روی این گره، با عدد واقعی
node src/cli.js race --profile /etc/savak/profile.json --node fra-1 --repeat 3

# ۲. مقایسهٔ دو سیاست، بدون تغییر شبکه
node src/cli.js plan --mode speed  --access cellular --pretty | head -20
node src/cli.js plan --mode stealth --access cellular --pretty | head -20

# ۳. پروب UDP/افت/پرت روی مسیر خودتان (به پاسخ‌دهندهٔ node نیاز دارد)
node src/cli.js probes --host fra1.example.com --udp-port 20125 --tcp-port 20126

# ۴. داشبورد: هر اسلایدر، کل موتور را دوباره اجرا می‌کند
node src/cli.js serve --port 8080
```

`race` سه چیز را جدا نشان می‌دهد: **پایین‌روندهٔ اندازه‌گیری‌شده**، **RTT**، و **افت**. عددی
که به دست می‌آید با `link.source: measured` به موتور برمی‌گردد؛ تا آن لحظه از مدل استفاده
می‌شود و UI این را با برچسب «تخمینی» می‌گوید. جعلِ measurement بهتر از نداشتنش نیست.

## باورهای غلط که این repo عمداً انجام نمی‌دهد

| ادعا | واقعیت در اینجا |
|---|---|
| «Multiplexing = سرعت بیشتر» | mux فقط handshake کم می‌کند؛ روی لینک پرافتطاع، head-of-line blocking یک اتصال مشترک افت را برای **همهٔ** جریان‌ها پخش می‌کند. `multiplex` را فقط برای rung‌هایی emit می‌کنیم که واقعاً سود می‌برند. |
| «`fragment` همیشه کمک می‌کند» | تکه‌تکه کردن recordها یعنی بایت و CPU اضافه؛ فقط وقتی emit می‌شود که DPI بستهٔ plain را می‌خواند (`sni-only`). |
| «100% MTU = 1500» | روی موبایل ۱۵۰۰ یعنی fragmentation. از `link.mtuCap` می‌خوانیم. |
| «هرچه buffer بزرگ‌تر، بهتر» | bufferbloat. KISS: کفِ محاسبه‌شده با BDP، نه بینهایت. |
| «UDP همیشه سریع‌تر است» | اگر path UDP را throttle کند، UDP یعنی ۴۰٪ افت و ۳ برابر handshake. `udpThrottled` آن پله را حذف/تنبیه می‌کند. |
| «kernel offload = رایگان» | `kernel_rx` در 1.14 طبق مستندات **کُندتر** است؛ emit نمی‌شود. kTLS TX فقط با kernel ≥5.7 و اگر واقعاً فعال باشد. |
| «یک پروتکل جدید همه‌چیز را حل می‌کند» | رتبه‌بندی بر پایهٔ اندازه‌گیری، همان‌طور که در `smart-evasion.md` آمده. |

## اگر اتصال کند است، به این ترتیب چک کنید

1. `savak plan` را با لینک فعلی اجرا کنید: آیا پلهٔ انتخابی با `reason` درست است؟
2. `link.source`: اگر `synthesized` است، یعنی پروب‌ها به گره نرسیده‌اند — اول firewall/پورت
   پاسخ‌دهنده (`20125/udp`) را چک کنید.
3. سمت سرور: `sysctl net.core.rmem_max` و `cat /proc/sys/net/ipv4/tcp_congestion_control`.
4. MTU مودم: اگر ۱۴۰۰ یا کمتر است، QUIC rungs حذف می‌شوند — این باگ نیست، انتخاب است.
5. اگر همه درست بود و هنوز کند است: گلوگاه، لینک شماست. هیچ پروتکلی معجزه نمی‌کند؛
   ولی `mode: resist` حداقل کاری را می‌کند که افتِ ناشی از pacing مصنوعی را نداشته باشید.
